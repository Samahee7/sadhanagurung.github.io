Habitual

Mobile shopping app · Full-cycle UX/UI design & prototype

Most shopping apps show every shopper the same catalogue — the same homepage, the same "trending" shelf, no sense of what any one person actually wants. Habitual is a concept for a shopping app that gets to know a shopper's taste from the very first screen, then shapes the whole experience around it.

Research & discovery: Competitive audit Problem framing Onboarding flow mapping

The problem

Generic product feeds make shoppers dig through irrelevant results instead of finding things they'd actually want.

The approach

Front-load personalization: ask about goals and interests during onboarding, then shape the feed, wishlist, and recommendations around it.

My role

End to end — wireframes, UI design, and a full interactive prototype, built to practice the complete process.

Stage 1Onboarding & personalization

The first-run flow names the problem before showing how curation fixes it. Registration doubles as a preference-gathering step that later shapes the home feed.

Stage 2Home, wishlist, profile & cart

The home feed surfaces sections built from onboarding signals. Wishlist, profile, and cart follow the same visual language throughout.

Stage 3Product, checkout & confirmation

Product and checkout keep the flow short: inline variant selection, single-screen checkout, and a lightweight confirmation moment.

Stage 4Search & filters

Search covers every state — default, active, filled, and empty — plus a filter overlay for sorting by price, category, and reviews.

What this project practiced

A self-directed, course-guided project — not shipped work — built to practice a complete mobile e-commerce flow start to finish, including empty and error states.

BizzFlow

Multi-tenant business management platform · Admin & client UX/UI design

Most small businesses juggle sales, stock, staff, and finances across separate tools that don't talk to each other. BizzFlow is a single platform to run all of it — with one catch: it needed to work for five completely different kinds of users, from the platform admin approving new businesses down to an employee ringing up a sale at the counter. I designed the two highest-stakes sides of that system: the internal Admin panel and the Client (business owner) experience.

Research & discovery: Role & permission mapping Multi-tenant flow diagramming Information architecture

The problem

One platform, five roles (admin, moderator, client, employee, customer) each needing a different level of access and a completely different pace of use — without the interface ever feeling like five separate products.

The approach

Design role-first: map what each user is allowed to see and do before touching a single screen, then build a shared visual system flexible enough to hold a dense analytics dashboard and a fast, low-friction setup flow.

My role

Solo — permission-model thinking, IA, and full UI design for the Admin and Client sides, including the onboarding and business-setup flows that feed into both.

Stage 1Onboarding & role selection

The very first screen asks one question — how will you use the platform — and splits the entire experience from there. Each path (Client vs. Moderator) then collects only what's relevant to that role, in short steps rather than one long form.

Stage 2Verification request

Because moderators and businesses both need to be vetted before they get real access, the request flow is broken into clear steps with visible progress, collecting identity details up front so OTP verification isn't a dead end later.

Stage 3Admin dashboard & analytics

The Admin's job is oversight, not daily operation — so the dashboard leads with the numbers that matter for running the platform itself: registered businesses, pending approvals, total users, and subscription revenue trending over the year, backed by role and plan distribution at a glance.

Stage 4User management & permission detail

Every user on the platform — moderators and clients alike — lives in one searchable, filterable table. Opening a user slides in their full profile: contact info, assigned roles, and every individual permission they hold, so an admin can audit or adjust access without hunting through separate screens.

Stage 5Admin profile

A dedicated profile view separates the admin's own account security (password, recovery email) from a live feed of recent platform activity — verifications, role changes, bans — so accountability is visible in the same place identity is managed.

Stage 6Business setup

Once approved, a client's first real task is registering their business. The form is split into a short, guided wizard with a "skip for now" escape hatch, because a new business owner shouldn't have to stop and find their PAN/VAT number just to see what the platform can do.

Stage 7Client dashboard

The Client dashboard flips the priority from platform oversight to business health: today's revenue and expenses, employee and branch counts, and a live feed of what just happened across the business — new hires, branch verifications, subscription changes — all before the owner scrolls once.

Stage 8Client analytics & reporting

For a multi-branch business, "how are we doing" is a harder question than one number can answer — so analytics break revenue and expense down by month, by branch, and by category, plus a dedicated profit-and-loss view, all filterable so an owner running five branches isn't stuck reading data for the other four.

Stage 9Profit & loss, expense breakdown

Deeper financial views — profit-and-loss trend, expense category breakdown, and revenue-vs-expense by branch — round out the reporting suite, giving an owner the kind of view they'd otherwise need a separate accounting tool for.

What this project practiced

Designing for permission depth without letting the interface feel bureaucratic — a checkbox-and-role model underneath, a clean dashboard on top. Client project; employee, customer, and moderator-side screens are still in progress.
